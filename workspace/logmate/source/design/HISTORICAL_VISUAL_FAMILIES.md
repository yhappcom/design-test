# LogMate Historical Visual Families — Failure & Reuse Matrix

Status: ACTIVE SYNTHESIS INPUT
Date: 2026-09-19
Purpose: force future design work to consume prior successes/failures instead of rediscovering them.

## Family F1 — Titanium Ledger / Instrument Archive

Observed strengths:
- strongest authored identity among historical explorations;
- disciplined datum/rule hierarchy;
- strong tabular/numeric presence;
- dense ledger can remain visually calm;
- clear distinction between editorial UI and operational data;
- strong continuity between Home summary and dense ledger in some specimens.

Observed failures / unsupported assumptions:
- low-luminance-only appearance became identity rather than one tested rendering mode;
- aircraft/cockpit/watch/route imagery carried too much brand meaning;
- `Titanium Ledger`, slogans and lifestyle language were not product-authority decisions;
- some specimens invented navigation/features such as Map/Aircraft/Currency/Reports;
- career/lifetime hero metric exceeded current product semantics;
- custom typography direction was visually persuasive before production type evidence closed;
- some Add Flight experiments removed section containment later reconciled against the confirmed UI contract.

Current standing:
REFERENCE — harvest numeric discipline, datum/rule hierarchy, authored calmness.
NOT CANONICAL — do not inherit appearance, slogans, imagery, IA or unsupported hero semantics.

## Family F2 — Bright daylight / Blue proposal

Observed strengths:
- daylight readability;
- explicit Home information hierarchy;
- clear action/search/recent/totals separation;
- usable table/search/filter visualization;
- easier transition to conventional mobile interaction patterns.

Observed failures / unsupported assumptions:
- bright blue became a new visual identity not derived from selected product baseline;
- repeated cards/KPI surfaces flattened hierarchy;
- hero aviation imagery returned as atmosphere;
- persistent bottom navigation appeared despite no canonical authorization;
- some portfolio text acted like marketing copy rather than product UI;
- screen coherence came from repeated card styling rather than stable datum/semantic grammar.

Current standing:
REFERENCE — harvest readable daylight composition and some information-order studies.
NOT CANONICAL — blue identity, cards, hero imagery and navigation assumptions do not transfer automatically.

## Family F3 — Previous Total detailed interaction family

Observed strengths:
- strongest state completeness;
- explicit zero vs carry-forward;
- blank != zero;
- H+MM entry;
- local error;
- field-addition semantics;
- large-text and keyboard-pressure thinking;
- import/baseline semantic work grounded in newer product direction.

Observed failures / incomplete transfer:
- visual styling was created before a selected whole-product baseline;
- teal/green selection treatment became an isolated mini-system;
- generic form/card appearance remained;
- the surface was optimized locally without enough Home/Add Flight/View visual inheritance.

Current standing:
SEMANTIC / INTERACTION REFERENCE — preserve state model and input behavior.
VISUAL OPEN — must inherit the selected whole-product baseline later.

## Family F4 — Broad portfolio boards

Observed strengths:
- useful as a checklist of required surfaces and cross-platform scope;
- exposed monetization and PWA/Settings gaps.

Observed failures:
- generated too many unresolved screens in one pass;
- image generation filled unknowns with new colors, cards, slogans, imagery and navigation;
- presentation-board coherence was mistaken for product-system coherence;
- local detail feedback caused global visual regeneration.

Current standing:
REJECTED AS VISUAL DIRECTION.
May be used only as scope/checklist evidence.

## Cross-family finding

The inconsistency is not simply `dark vs light`.

Each family redefined a different subset of:
- brand carrier;
- density;
- navigation;
- container model;
- typography;
- numeric grammar;
- image policy;
- action hierarchy;
- state representation.

Because no selected baseline owned these dimensions, later work treated all dimensions as open every time.

## Reuse rule

Future candidate generation must explicitly list for each borrowed pattern:
- source family;
- exact property being reused;
- reason it survives current product/research evidence;
- what from the same family is deliberately NOT inherited.

No family may be imported wholesale.

## Candidate construction matrix

Every full candidate must resolve the following dimensions once, coherently:

1. Appearance strategy
2. Surface hierarchy
3. Typography role system
4. Numeric/data typography
5. Container/rule grammar
6. Primary/secondary action grammar
7. Search/input grammar
8. Navigation/chrome
9. Icon policy
10. Image/illustration policy
11. Density progression
12. Responsive recomposition
13. Focus/error/selection state grammar
14. Ad boundary
15. Native/PWA continuity

A candidate that leaves these to the image generator is invalid.

## Drift detector

A revision is rejected as drift if it changes any dimension above that was not:
- explicitly requested by owner;
- required by canonical product change;
- required by implementation/runtime evidence;
- required by proven cross-screen failure.

This detector applies even if the new revision looks more polished.
